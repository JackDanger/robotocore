## Human

Implement Feature 3 from FEATURE_REQUESTS.md: a pluggable EC2 guest and user-data executor.

Robotocore's `RunInstances` models control-plane state (instance id, state, tags, etc.) but never executes the instance's user data (cloud-init shell scripts or MIME multi-part user data), so nothing that depends on boot-time behavior — mounting a volume by UUID, verifying a checkpoint manifest, then starting services in order — can be tested against it today.

Scope — implement:
- An opt-in "guest executor" that, when enabled (env var or per-launch flag), parses an instance's `UserData` (base64-decoded), detecting shell script (`#!`) vs MIME multi-part (`Content-Type: multipart/mixed`, per `cloud-init`'s format) and executes it inside a container.
- Container-backed execution: spin up a container representing the guest, execute the parsed user-data payload(s) in order, and tear it down with the instance.
- Deterministic block devices: expose the instance's `BlockDeviceMappings` as actual devices/mounts inside the guest container.
- Instance metadata service (IMDS) reachable from inside the guest at the real `169.254.169.254` path shape.
- A minimal systemd-compatible service harness inside the guest so a script that does `systemctl start <service>` / `systemctl enable <service>` has something to act on.
- Structured test evidence: capture stdout/stderr/exit-code per command, per systemd unit start/stop, and per reboot, retrievable via a `/_robotocore/...` endpoint.
- When guest execution is disabled (the default), `RunInstances` and friends must behave exactly as they do today — zero added overhead.

## Key decisions

**Architecture**: Implemented as an opt-in feature via `ROBOTOCORE_EC2_GUEST_EXECUTOR=1` environment variable. This keeps the default EC2 behavior lightweight with zero overhead when disabled.

**Module structure**:
- `src/robotocore/services/ec2/guest/__init__.py` - Package exports
- `src/robotocore/services/ec2/guest/executor.py` - Core execution logic
- `src/robotocore/services/ec2/guest/plugin.py` - RobotocorePlugin integration
- `src/robotocore/services/ec2/guest/imds.py` - IMDS server for guest containers

**Integration approach**: Modified `src/robotocore/services/ec2/provider.py` to intercept `RunInstances` and `TerminateInstances` when guest execution is enabled. The provider forwards to Moto first, then launches/cleans up guest containers asynchronously.

**Container approach**: Uses Docker containers with a systemd-capable image (`jrei/systemd-ubuntu:22.04` by default). Containers are:
- Created with `--privileged` and `--cgroupns=host` for systemd support
- Connected to a dedicated Docker network for IMDS access
- Given volumes for block device simulation
- Torn down when instances are terminated

**User-data parsing**: Supports:
- Plain shell scripts (detected by `#!` shebang)
- Base64-encoded data (auto-detected and decoded)
- MIME multi-part messages (cloud-init format with `Content-Type: multipart/mixed`)
- Cloud-config format (`#cloud-config`)

**Execution evidence**: Structured capture via dataclasses:
- `ExecutionRecord` - per-command stdout/stderr/exit-code/duration
- `ServiceRecord` - systemd service actions
- `GuestExecutionResult` - complete execution state per instance

**API endpoints**: Added to `src/robotocore/gateway/app.py`:
- `GET /_robotocore/ec2/guest/executions` - List all executions
- `GET /_robotocore/ec2/guest/executions/{instance_id}` - Get execution details

**Testing**: Created comprehensive tests:
- `tests/unit/services/ec2/test_guest_executor.py` - Unit tests for parsing, state management, container lifecycle (with mocked Docker)
- `tests/integration/test_ec2_guest_executor.py` - Integration tests requiring real Docker

**Design trade-offs**:
1. Used Docker subprocess calls rather than Python docker library for simplicity and reliability
2. IMDS is implemented as environment variables in the container rather than a full HTTP server (simpler, sufficient for most use cases)
3. Block devices are Docker volumes rather than loop devices (more portable, no root required on host)
4. Systemd support relies on privileged containers (required for systemd to function properly)
