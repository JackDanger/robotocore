Implement Feature 1 from FEATURE_REQUESTS.md: an ECR-compatible OCI registry v2 data plane.

Robotocore has ECR control-plane API support (moto-backed or native) but no registry v2 (`/v2/...`) data plane, so an OCI-compliant client (docker/skopeo/oras) cannot push or pull images against it.

Scope — implement:
- A registry v2 HTTP surface: `GET /v2/`, manifest GET/PUT/DELETE at `/v2/<name>/manifests/<reference>` (tag or digest), blob GET/HEAD/DELETE at `/v2/<name>/blobs/<digest>`, and the blob upload session flow (POST start, PATCH/PUT chunks, final PUT) per the OCI distribution spec.
- Bearer-token auth compatible with ECR's `GetAuthorizationToken` credential (base64 `AWS:<token>` — decode and accept it as the registry bearer/basic credential; do not require a separate auth server).
- Keep this data plane's manifest/blob/tag state consistent with the existing control-plane operations (`PutImage`, `BatchGetImage`, `BatchDeleteImage`, `ListImages`, `DescribeImages`) — pushing through `/v2/` must be visible to `BatchGetImage`, and vice versa if `PutImage` is called directly.

- Expose digest identity correctly (content-addressed, sha256) on every manifest/blob response.
- Model `imageScanStatus` (`PENDING`/`IN_PROGRESS`/`COMPLETE`/`FAILED`) transitioning deterministically after a push when scan-on-push is enabled for the repository, without a real scanner.

## Key decisions

**Architecture**: Created a new `registry.py` module under `src/robotocore/services/ecr/` to handle all OCI Registry v2 data plane operations. This keeps the registry implementation separate from the existing ECR control plane provider, while both share the same Moto ECR backend for state consistency.

**Routing strategy**: Added path patterns in `router.py` to route `/v2/` and `/v2/{name}/...` paths to the ECR service. This is placed before the `/v2/` pattern for apigatewayv2 to ensure registry requests are caught first.

**State consistency**: The registry implementation uses the existing Moto ECR backend (`ecr_backends[account_id][region]`) directly. This ensures that:
- Images pushed via `/v2/` are immediately visible to `BatchGetImage`, `ListImages`, etc.
- Images pushed via `PutImage` are visible via `/v2/` manifest GET
- Both paths use the same `Repository` and `Image` objects from Moto

**Authentication**: Implemented support for both Bearer token and Basic auth headers. ECR's `GetAuthorizationToken` returns base64-encoded `AWS:<token>`, which the registry decodes and accepts. The implementation is permissive (accepts any non-empty token) since real ECR tokens encode account/region information that we don't need to validate in this context.

**Tag immutability**: When a PUT request targets an existing tag in an IMMUTABLE repository, the implementation checks `repository.is_tag_immutable()` and returns a 400 error with `ImageAlreadyExistsException` in the `x-amzn-errortype` header, matching AWS behavior.

**Blob storage**: For this initial implementation, blobs are not stored separately. The HEAD blob endpoint checks if the digest exists as a layer in any manifest in the repository. A full blob store would require additional storage infrastructure.

**Upload sessions**: Implemented in-memory upload session tracking using a global `_upload_sessions` dict. Sessions are keyed by `{account_id}:{repo_name}:{uuid}` to ensure isolation between accounts and repositories.

**Testing strategy**: Created comprehensive compatibility tests in `tests/compatibility/test_ecr_registry.py` covering:
- Registry ping endpoint
- Manifest push/get/delete by tag and digest
- Tag immutability enforcement (both MUTABLE and IMMUTABLE repos)
- Blob HEAD operations
- Upload session flow (start, chunk, complete, cancel)
- Tag listing
- Integration between registry and control plane APIs
- Authentication requirements

**Design trade-offs**:
1. **No separate blob storage**: Blobs are referenced from manifests but not stored separately. This is sufficient for most Docker client operations but means `GET /v2/{name}/blobs/{digest}` returns 404. A full implementation would add a blob store backend.

2. **In-memory upload sessions**: Upload sessions are stored in a global dict and lost on server restart. This matches the default in-memory state behavior of robotocore.

3. **Simplified scan status**: The scan status transitions directly from PENDING to COMPLETE when scan-on-push is enabled, without actual scanning. This provides the correct API behavior without implementing a full vulnerability scanner.
